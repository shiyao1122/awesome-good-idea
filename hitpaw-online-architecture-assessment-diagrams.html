HitPaw Online 后端架构与承载能力评估

面向后续流量增长，评估当前架构的技术债务、扩容瓶颈、跨地域风险与平台化方向。

汇报版 范围：HitPaw Online 后端 假设：长期日常流量增长

0. 评估结论

本次评估关注 HitPaw Online 后端在后续流量增长下的承载能力。评估对象是业务后端与中间件链路，不评价第三方 Provider、内部 AI 服务、账号体系-中台服务本身的产能。

技术债务
  1. HitPaw Online 过去承接了多项业务，相同功能存在多处、多种实现。
  2. 任务状态、回调、Provider 接入、权益规则等核心逻辑分散。
  3. 历史兼容逻辑持续沉淀，代码劣化，旧代码不敢改、难下线。
承载能力瓶颈
  1. 核心链路是同步创建任务、异步消费执行，洪峰下主要风险是 MQ 或内部队列积压。
  2. 不同任务压力模型不同，包括媒体后处理、Provider 轮询、回调峰值、高频状态查询；ffmpeg 类操作会尽量使用计算资源加快处理，资源受限时更可能表现为处理变慢。
  3. 单纯扩容单体会同时扩 API、Worker、Callback、Cron，无法只扩真正瓶颈，容易造成资源浪费。
首轮压测观察
  1. 当前测试环境在 Mock 外部服务的前提下，可承接约 250 QPS 的 VEN 创建请求且未出现错误。
  2. 高并发下尾延迟已明显不稳定，P99 达到秒级，最大耗时超过 8s，说明系统已出现排队或资源争用风险。
  3. 该结果仅反映测试环境与 Mock 链路下的表现，不能直接代表生产环境真实承载能力，需要继续复测和定位瓶颈。
跨地域风险
  1. 美国为主流量地域，但 MySQL 在新加坡，Auth 等 MySQL 查询存在稳定跨地域访问。
  2. 每次 Auth 查询 usersession / users 预估超过 400ms，所有依赖 MySQL 的查询都会被放大。
  3. 该问题影响较大，需要专项讨论数据库地域、读写规划和迁移方案；当前可确认方向是尽量减少稳定跨地域调用。
处理原则
  1. 拆分不是目的，模块化单体本身不是核心问题。
  2. 短中期重点是梳理业务边界、任务边界、队列边界和观测边界。
  3. 长期沉淀任务平台、Provider 接入、媒体处理、观测成本等可复用能力。
一、当前系统现状

1.1 业务主链路对比：用户流程不变，内部承载路径改变

二、主要架构问题

问题总览

问题归口 当前表现 对承载能力的影响
历史代码劣化 HitPaw Online 过去承接了多项业务，相同功能存在多处、多种实现，兼容逻辑持续沉淀。 这不是直接的承载瓶颈，但会让需求变更、问题修复和能力复用变慢；即使不做架构重构，也需要持续治理。
扩容粒度 异步任务压力模型不同，但当前只能整体扩容单体或同一类 Worker。 流量增长后只能整体扩容，无法针对队列积压、回调高峰、媒体处理或状态查询分别扩容。
首轮压测观察 测试环境在 Mock 外部服务后，VEN 创建接口约 250 QPS 下错误率为 0%，但 P99 达到秒级，最大耗时超过 8s。 说明高并发创建任务场景下已出现排队或资源争用风险；该结果不能直接代表生产环境，需要后续构建更完整的压测基线。
跨地域访问 美国主流量访问新加坡 MySQL；新加坡消费者访问美国 Redis / RabbitMQ / OSS。 美国主流量的基础耗时被跨地域 MySQL 放大；方案影响较大，需要专项研究，当前方向是减少稳定跨地域调用。

2.2 扩容问题：异步任务压力模型不同，单体扩容粒度粗

同步接口创建任务 鉴权 / 权益预扣 / 写任务状态 / 投递 MQ / 返回 taskId
流量增长后，大量任务进入 MQ 或内部队列
RabbitMQ / Redis 队列 任务积压主要发生在异步队列中
同一单体 Worker / Poller 承接不同压力模型
Backend Pod 内部 Worker / Poller
媒体计算 / 后处理型 ffmpeg / ffprobe / 转码 / 合成 / 剪切 / 混音 ffmpeg 倾向于尽可能使用更多计算资源加快处理；并发升高时不一定直接打爆 CPU limit，也可能表现为单任务处理速度变慢、队列恢复时间变长。
Provider 轮询 / 搬运型 轮询第三方结果 / 下载上传结果文件 / 状态推进 示例：AI 视频生成、图片生成、音乐生成
内部服务回调型 接收回调 / 幂等 / 状态竞争 / Redis & MySQL 更新 示例：视频增强、图片增强、换脸、去水印等回调链路
高频状态查询型 轮询 / WS / 历史列表 / 任务状态读取 压力点：Redis QPS、热点 key、连接数、跨地域 MySQL 查询

3.3 跨地域治理：减少稳定跨地域调用，数据库方案需专项研究

数据库地域治理 结合美国主流量策略，专项评估 MySQL 迁移到美国、同地域读写规划或其他减少跨地域查询的方案。
队列与任务状态地域治理 评估 Redis / RabbitMQ / OSS 与消费者部署地域的一致性，减少备地域消费者稳定跨地域消费。
消费者部署策略 明确美国主、新加坡备场景下是否两地都需要运行 Consumer；必要时按地域开关控制消费者。
跨地域观测 补充 Auth 查询、MySQL 查询、Redis / MQ / OSS 访问的地域维度耗时指标。
